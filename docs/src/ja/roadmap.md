# アーキテクチャ改善計画

次の順序は動作するテンプレートから本番コマースへ発展させるための**提案**で、現在の実装ではありません。

1. **商品と価格の権威をサーバーへ。** 金額を最小通貨単位の整数か精密 Decimal にし、商品版と在庫責務を定義します。見積 API は ID と数量だけを受け、最新価格・在庫と期限/版を返します。ブラウザーカートは購入意図を保存しますが、確定価格を保存しません。中英日の編集・欠落時 fallback も定義します。
2. **カート削除前に注文作成。** 認証付き `POST /orders` と一意の冪等キーを導入します。1 トランザクションで在庫を確保し、注文と不変の明細を保存して、注文 ID とサーバー合計を返します。その後に提出済みカート行だけを消します。重複、価格変更、在庫不足、rollback を検証します。
3. **決済を非同期の状態機械へ。** 支払試行は注文とサーバー金額に紐付け、事業者 Webhook の署名と重複を確認します。成功、失敗、期限切れの遷移を明示し、失敗時に在庫を解放します。事業者とその現行契約を選定してから実装します。
4. **取り消し可能なセッションへ。** Cookie/CSRF または資格情報の更新方針、失効、ログアウト、ログイン制限、保護された mutation のサーバー確認を追加します。ブラウザー保存のユーザーを認可根拠にしません。
5. **SSE 境界の背後に Provider。** サーバー側モデルインターフェース、コスト・出力制限、abort、途中エラーイベント、request ID ログを追加します。会話保存は必要な場合だけ Repository と保持規則を決めます。生のモデル HTML を描画しません。
6. **運用と検証。** リクエスト、DB、決済、AI の request ID を接続します。デプロイ構成が決まったら health/readiness を追加し、使い捨て PostgreSQL で migration と競合を検証します。3 種の UI に注文、再試行、言語、セッション失効、Provider 障害の E2E を加えます。契約変更では英語を先に書き、中国語・日本語を同期します。
