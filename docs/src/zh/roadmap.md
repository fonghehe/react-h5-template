# 架构改进路线

下面是从可运行模板发展到真实电商服务的建议顺序，**不是当前已实现功能**。

1. **权威商品与价格。** 将金额改成最小货币单位整数或精确 Decimal，明确商品版本与库存归属。服务端报价只收商品 ID、数量，查询最新价格和库存，返回版本或报价过期时间；浏览器购物车继续表达用户意图，不表达权威金额。为中英日商品内容建立编辑与回退规则。
2. **先建订单再清购物车。** 增加需认证的 `POST /orders` 与唯一幂等键，在事务中预留库存并写订单及不可变订单行；成功响应给订单 ID 和服务端总额。仅成功后删除已提交的购物车行。测试重复提交、改价、缺库存及事务回滚。
3. **支付状态机。** 支付尝试关联服务端订单金额，验证服务商 Webhook 签名、去重事件；已支付、失败、过期的状态转换必须明确，失败/过期释放库存，重放不能重复扣款。支付服务商的实际契约要在选定后再实现。
4. **可撤销会话。** 定义 Cookie/CSRF 或可轮换凭证策略、过期与退出行为、登录限流和服务端权限检查。语言与购物车仍可本地保存，但浏览器缓存用户不能成为授权依据。
5. **模型 Provider。** 增加服务端接口、输出和成本限制、请求 ID 日志、中止与流中错误事件；只有需求确实需要才新增会话持久化与保留策略。模型文本不能直接渲染原始 HTML。
6. **运行与验证。** 串起请求 ID、仓储、支付及 AI 日志；在确定部署拓扑后补健康/就绪检查；用可销毁 PostgreSQL 验证迁移和并发；三套 UI 都覆盖订单、重试、语言切换、会话过期与 Provider 异常旅程。每次契约变更先补英文文档，再同步中文和日文。
